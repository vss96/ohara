# v0.11 — CoreML fixed-shape embedder investigation

**Date:** 2026-06-12/13 · **Hardware:** Apple M4 Pro (8P+4E, 24GB), macOS 26.4
**Harness:** `tests/perf/coreml_matrix.rs` · **Stack:** fastembed 5.13.4 /
ort 2.0.0-rc.12 / onnxruntime 1.24.2

## Context

The questdb baseline (5,978 commits / 121,243 hunks) indexed in 3,390s wall;
the embed stage consumed 22,943s of 26,069s total CPU (87%) at ~677%
parallelism — embedding is the only lever that matters. Measured on the real
index: 98.6% of hunks have unique diff text (embed-cache ceiling ≈ 1.4%),
avg semantic text 4,660 chars, 33% of rows > 2,000 chars (saturating the
512-token cap).

## Sustained leak probe (the plan-7 question)

`fp32-coreml-fixed` b32, 500 batches of fresh salted rows, phys_footprint
sampled every 50:

```text
iter   0: 3228.1 MB   (post-compile transient)
iter 100: 2084.3 MB
iter 450: 2085.0 MB   → +0.7MB over 350 batches ≈ 2KB/batch (noise)
```

vs the v0.6.1 diagnosis of ~4.3MB/batch with the dynamic path. Conclusion:
the historical "leak" was CoreML shape-specialization churn — pad-to-longest
tokenization gives nearly every batch a distinct (batch, seq) shape and
CoreML retains a compiled specialization per shape. One fixed shape → one
specialization → flat footprint.

## Root causes, in one place

1. ort's default CoreML EP config is the legacy **NeuralNetwork** format;
   `LayerNormalization`/`Gelu` exist only in **MLProgram**. The shipping
   CoreML path never could run BGE well.
2. The CoreML EP supports **no quantized ops**, so the INT8 default model is
   unacceleratable by construction.
3. onnxruntime 1.24.2's conversion emits **unbounded dimensions** unless the
   ONNX graph itself has fixed dims; the ANE rejects unbounded graphs and
   the CoreML-CPU fallback is unstable (onnxruntime#21227 class).
4. Fix: `make_dynamic_shape_fixed`-style patching (`batch_size→32`,
   `sequence_length→512`, graph inputs+outputs) + `PaddingStrategy::Fixed(512)`
   + 32-row batch padding. fp32 weights, MLProgram, `ComputeUnits::All`.

## Costs

- One-time ~27s CoreML compile per process (first `embed_batch` session
  load); first fp32 model download ~130MB.
- Short rows pay the full 512-token cost (flat 118 rows/s regardless of
  length); on the mixed corpus the net win vs CPU is ~2.9×.
- Steady-state footprint ~2.1GB while embedding (foreground `ohara index`
  only; the daemon never loads CoreML).

## Projection

Embed at 3.05× → questdb full index ~56 min → **~20 min** (embed is 87% of
total work; storage unchanged).

## Reproduce

```sh
# full matrix (CPU + the three broken CoreML configs die loudly):
cargo test -p ohara-perf-tests --release --features coreml \
    --test coreml_matrix -- --include-ignored --nocapture

# the shipping configuration:
python -m onnxruntime.tools.make_dynamic_shape_fixed --dim_param batch_size --dim_value 32 model.onnx tmp.onnx
python -m onnxruntime.tools.make_dynamic_shape_fixed --dim_param sequence_length --dim_value 512 tmp.onnx fixed.onnx
MATRIX_UNIFORM=1 MATRIX_BATCH=32 MATRIX_CORPUS=512 MATRIX_SUSTAIN=500 \
MATRIX_FIXED_ONNX=fixed.onnx MATRIX_CONFIGS=fp32-coreml-fixed \
cargo test -p ohara-perf-tests --release --features coreml \
    --test coreml_matrix -- --include-ignored --nocapture
```
